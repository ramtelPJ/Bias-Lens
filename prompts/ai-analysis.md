# AI article analysis pipeline

## Goal

Implement the AI analysis pipeline (AGENTS.md §19): a `POST /api/analyze` route that finds articles with no `article_analyses` row (LEFT JOIN pending-detection, never `analyzed_at IS NULL` alone), analyzes each with the OpenAI provider via the Vercel AI SDK, validates the output with Zod, saves a row to `article_analyses`, and sets `analyzed_at` only after a valid save. Processes in configurable batches, continues until no pending articles remain by default, and returns/logs a run summary.

Out of scope (future prompts): pgvector/embeddings (§20), Oxylabs Scheduler (§18), any analysis-trigger UI.

## Decisions / assumptions

- **Model**: `gpt-5.4-mini` — a current, cost-appropriate tier for a per-article batch job (not the bleeding-edge `gpt-6-astra`/`gpt-5.6-*` codename releases, not a legacy model). Stored in `article_analyses.model` per article, so it's easy to change later; flag if you'd rather use a different model.
- **`disclaimer` is a fixed constant**, not AI-generated: `"This political framing and sentiment analysis is generated by AI and represents an estimate, not an objective fact."` Asking the model to author its own legal/compliance-style disclaimer per article risks inconsistent wording; the column still gets populated per article as the schema requires.
- **`bias_score` is computed in code**, not requested from the model: `(rightPercentage - leftPercentage) / 100`, per §19's explicit formula. The model only produces the three percentages and the label.
- **Pending-article lookup**: fetches all articles with an embedded `article_analyses(id)` (no filter on the embedded resource, per the supabase skill's documented gotcha) and filters client-side for an empty embed, oldest-`scraped_at`-first. This scans the whole `articles` table each call — fine at current/expected scale for this project; flagged with a `ponytail:` comment as the ceiling to revisit (a `NOT EXISTS` SQL view/function) if the table grows very large.
- **Retry policy**: any failure analyzing a given article (invalid Zod output **or** an OpenAI API error) gets exactly one retry, then the article is marked failed and skipped — no bad row is ever saved, matching §19's "retry once or mark the article as failed."
- **Duplicate safety**: inserting `article_analyses` treats a unique-constraint violation on `article_id` (e.g., an explicit `articleIds` request naming an already-analyzed article, or a race with a concurrent run) as a skip, not a failure — same pattern as the scraping pipeline's URL dedupe.
- **Batching model**: matches §19 literally — a single `POST /api/analyze` call loops internally over batches until no pending articles remain (when no explicit `articleIds`/`limit` is given), rather than only doing one batch per HTTP call. This is a manually-triggered internal/admin action, so a longer-running request is acceptable; no background job queue is introduced (that would be overbuilding for what AGENTS.md asks).

## Implementation requirements

- Pending-analysis detection (§19 required behavior #1): an article is pending only when no `article_analyses` row exists for it — never rely on `analyzed_at IS NULL` alone.
- Default behavior processes **all** pending valid articles, looping in batches of `ANALYSIS_BATCH_SIZE` (env, default 5) or the request's `batchSize`, until none remain. An explicit `articleIds` list processes exactly those (still skipping any that already have an analysis).
- AI output schema (Zod), field names matching AGENTS.md §19 exactly: `summary`, `sentimentScore` (-1..1), `sentimentLabel` (enum), `politicalFramingLabel` (enum: left/center/right/mixed/unclear), `leftPercentage`/`centerPercentage`/`rightPercentage` (0..100 each), `.refine()` enforcing they sum to 100 (±1 tolerance for float rounding), `confidence` (0..1), `framingNotes`, `loadedTerms` (string array, may be empty).
- System prompt must instruct the model to: use only the article text as evidence (never infer from the outlet name), keep the summary neutral, match `politicalFramingLabel` to the strongest percentage unless confidence is low or percentages are close (then prefer `mixed`/`unclear`), and list only loaded terms actually present in the text.
- On invalid output (Zod/refine failure, i.e. `NoObjectGeneratedError`) or an API error, retry exactly once with the same input; if the retry also fails, mark the article failed (log it, do not insert, do not touch `analyzed_at`) and move on.
- Save to `article_analyses`: model output fields as validated, plus computed `bias_score`, fixed `disclaimer`, and the model id string. Set `articles.analyzed_at = now()` only after the insert succeeds.
- Layering (§5): `app/api/analyze/route.ts` stays thin; all OpenAI/Zod/DB logic lives in `lib/ai`, `lib/pipeline`, `lib/supabase`.
- Method + admin-secret rules (§14/§15): `POST /api/analyze` only, `x-biasly-admin-secret` required, `401` on missing/invalid, never via query string.
- Console logging: batch started/completed, per-article analyzed/failed, and a final summary object logging analyzed/skipped/failed counts (§19 requirement #7/#8/#9).
- No `any` types; explicit types for the pipeline summary and AI output.

## Security requirements

- `OPENAI_API_KEY` and `SUPABASE_SERVICE_ROLE_KEY` are read only in server-only modules (`lib/ai/analyze-article.ts`, `lib/supabase/service-client.ts`) — never imported by client components.
- `app/api/analyze/route.ts` returns `401` on a missing/incorrect `x-biasly-admin-secret` header before any OpenAI call or DB read.
- Validate the optional request body with Zod; reject malformed input with `400`.

## Acceptance criteria

- `POST /api/analyze` without the admin-secret header returns `401` and makes no OpenAI calls.
- `POST /api/analyze` with a valid header and no body processes all 16 currently-pending Reuters articles across as many batches as `ANALYSIS_BATCH_SIZE` requires, without needing to be called more than once.
- Every inserted `article_analyses` row has `left_percentage + center_percentage + right_percentage` within rounding tolerance of 100, `bias_score` correctly derived, and a non-null `disclaimer`/`model`.
- `articles.analyzed_at` is set if and only if a corresponding `article_analyses` row was actually saved.
- Running the route again after a full run reports 0 pending articles processed (nothing left to analyze) rather than erroring or re-analyzing.
- `npm run typecheck` and `npm run lint` pass.

## Manual test steps (after implementation)

1. Confirm `OPENAI_API_KEY` is set in `.env.local` (already done) and the dev server is running (`npm run dev`, watch its terminal for `[analyze]` logs).
2. Trigger a full analysis run (all pending articles, default batch size):
   ```bash
   curl -X POST http://localhost:3000/api/analyze \
     -H "x-biasly-admin-secret: <your BIASLY_ADMIN_SECRET>" \
     -H "Content-Type: application/json"
   ```
3. Confirm the `401` path:
   ```bash
   curl -i -X POST http://localhost:3000/api/analyze
   ```
4. Spot-check a saved analysis:
   ```bash
   curl -s "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/article_analyses?select=bias_label,left_percentage,center_percentage,right_percentage,bias_score,sentiment_label,confidence&limit=5" \
     -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" \
     -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY"
   ```
5. Confirm previously-scraped articles now show up on the homepage (they only appear once `analyzed_at` is set — this is the first time that becomes true end-to-end).
6. Re-run step 2 and confirm the summary reports 0 articles analyzed (all pending work already done).
